# 平台治理三大痛点方案

> 2026-08-11 创建。三个痛点相互独立,拆为三个计划顺序执行,每个完成后压缩会话再启动下一个。

## 痛点速览

| # | 痛点 | 一句话目标 |
|---|------|-----------|
| ① | 盲推:不知哪条规则在生效,哪条是死规则 | 采集每条规则命中计数,自动标记死规则 |
| ② | dry-run 只预览规则,不知变更后流量通不通 | 变更前输入五元组,仿真命中路径与最终判定 |
| ③ | 只有单次任务快照,无法回退到一周前 | 节点级规则库版本档案,任意历史版本一键回滚 |

## 计划一:规则活性分析(命中率采集 + 死规则识别)

### 现状
- proto **已预留** `RuleHit{rule_id, hits}`(stream.proto:103)和 `AgentStats.rule_hits`(stream.proto:91),但未启用
- collector `SetRuleHits` 是**空桩**(collector.go:247,只打日志不采集)
- 采集命令 `iptables -S` **无计数器**;`IptablesRule` 模型无 pkts/bytes 字段
- **核心缺口**:MYFW 规则落盘不带 comment(iptables.go `buildRuleArgs` 第 613-689 行只生成 `-p/--dport/-j` 匹配体),iptables 计数器**无法反解到策略实例 ID**

### 方案
1. **规则标识**:driver 落规则时追加 `-m comment --comment "myfw:i<实例ID>"`,让每条 MYFW 规则可被反解
2. **Agent 采集**:collector 新增 `iptables -L -v -n -x` 采集,解析 pkts/bytes + comment,复用 RuleHit 通道上报
3. **Controller 存储**:新增 `RuleHitStat` 模型(node_id, instance_id, packets, bytes, last_seen),按 (node, instance_id) upsert
4. **死规则标记**:规则启用且 packets=0 且存活超阈值(默认 7 天)-> dead=true
5. **前端**:实例详情展示命中率列 + 死规则徽标 + "仅看死规则"过滤

### 改动清单
| 文件 | 改动 |
|------|------|
| proto/myfw/v1/stream.proto | StateReport 复用 rule_hits 或扩展 IptablesChain 带计数器 |
| internal/agent/driver/iptables/iptables.go | buildRuleArgs 追加 `-m comment --comment "myfw:i<id>"` |
| internal/agent/driver/nftables/nftables.go | nft comment 等价(nftables 原生支持 `comment` 关键字) |
| internal/agent/collector/collector.go | 实现 SetRuleHits + 计数器采集解析 |
| internal/model/rule_hit.go | 新增 RuleHitStat 模型 |
| internal/db/db.go | AutoMigrate |
| internal/controller/server/iptables_routes.go | 新增命中率查询 API |
| web/src/views/ | 命中率展示 |

### 风险与对策
- **comment 改变规则 hash**:存量规则无 comment,hash 不匹配会触发 drift。对策:hash 计算时排除 comment 段;或一次性全量重新下发收敛
- **nftables comment**:需验证 nft 驱动 comment 落盘与回读

### 工时:3-4 天 | 依赖:无 | 建议顺序:第 3(改动面最大)

## 计划二:流量仿真预演(规则匹配引擎)

### 现状
- dry-run 是 `CompileInstances` 生成 CompiledRule 列表(compiler.go:164),只预览"下发什么规则",不预演流量
- 无任何规则匹配引擎

### 方案
1. **纯逻辑匹配引擎**(新建 internal/controller/simulator/):
   - 输入:节点规则集(CompiledRule + CustomChain 挂载关系)+ 五元组流量(源/目的/协议/端口/接口)
   - 模拟 iptables 遍历:INPUT/FORWARD 钩子 -> MYFW 子链 -> 线性匹配 -> ACCEPT/DROP 终止 / RETURN 回父链
   - 支持:源/目的 IP/CIDR、地址组(set)成员、协议、端口范围、MARK 匹配
   - 输出:Trace(命中规则链路 + 每条匹配结果)+ 最终判定(ACCEPT/DROP/REJECT)
2. **API**:`POST /api/v1/simulate` 入参(node_id 或 rule_set, flow),返回 trace
3. **前端**:变更预览页加"流量预演"面板,填五元组 -> 展示命中路径树

### 改动清单
| 文件 | 改动 |
|------|------|
| internal/controller/simulator/engine.go | 匹配引擎纯函数 |
| internal/controller/simulator/engine_test.go | 表驱动测试(ACCEPT/DROP/RETURN/跨链) |
| internal/controller/server/simulate_routes.go | REST API |
| web/src/views/ 或 components/ | 流量预演面板 |

### 风险与对策
- **iptables 语义复杂**(NAT 改写影响后续匹配、conntrack):首版只做 filter 表无状态匹配,NAT/mangle 标注"不支持,仅展示规则"
- **地址组匹配**:需加载 AddressGroup 成员

### 工时:4-5 天 | 依赖:无 | 建议顺序:第 2

## 计划三:规则库版本档案(长期快照 + 任意时间点回滚)

### 现状
- `Snapshot`(task.go:59)绑定 TaskID,是单次 Apply 前 MYFW 备份,仅任务内回滚
- Agent 侧持有快照,Confirm/Rollback 后释放(coordinator.go:533,605)
- **无平台级长期版本档案**:一周后 Agent 早释放快照,无法回退

### 方案
1. **新增 NodeRuleRevision 模型**:
   - 字段:node_id, revision_no, payload(完整 MYFW 规则集 JSON), hash, source(apply/scheduled/manual), task_id, note, created_at
   - 触发:每次 Apply 成功后归档(从编译结果 + 实例快照重建)+ 定时归档(每日,可选)
2. **版本列表 API**:`GET /api/v1/nodes/:id/revisions` 分页返回历史版本
3. **回滚 API**:`POST /api/v1/nodes/:id/revisions/:no/rollback`:
   - 用该版本规则集作为 expected 生成新 Apply 任务(走正常保护期)
   - **回滚前自动归档当前版本**(便于"撤销回滚")
4. **保留策略**:默认保留最近 N 份(如 30)+ 最近 M 天(如 90 天),定时清理
5. **前端**:节点详情加"版本历史"页签 + 回滚按钮 + 二次确认

### 改动清单
| 文件 | 改动 |
|------|------|
| internal/model/node_rule_revision.go | 新模型 |
| internal/db/db.go | AutoMigrate |
| internal/controller/task/coordinator.go | Apply 成功后调用归档 |
| internal/controller/server/revision_routes.go | 版本列表 + 回滚 API |
| web/src/views/Nodes.vue | 版本历史页签 |

### 风险与对策
- **存储量**:SQLite 存全量规则集,每节点每变更一份。单节点规则通常百条级,N 份可接受;prod MySQL 无忧
- **回滚语义**:回滚=用旧规则集当 expected 下发,覆盖当前实例状态。对策:回滚任务单独标记 scene=revision_rollback,完成后重建实例 applied 状态

### 工时:3-4 天 | 依赖:无 | 建议顺序:第 1(最简单,风险最低)

## 执行顺序

三个痛点相互独立。建议顺序(风险从低到高):

1. **计划三(版本档案)**:无 proto/driver 改动,纯 Controller 侧 model+路由,风险最低,先落地
2. **计划二(流量仿真)**:纯逻辑无副作用,可独立验证
3. **计划一(命中率)**:涉及 proto + driver + collector + hash 兼容,改动面最大,放最后

每个计划按 TDD 红-绿-重构执行:
- 红:写 .feature/测试用例(覆盖正常/边界/异常)
- 绿:最少代码通过
- 重构 + 同步 code-analysis.md

完成后压缩会话,再启动下一个。
