## P1(严重,确定性):恢复实例与新任务下发规则集不一致

### 根因
`approveAndDispatch` 的执行顺序(coordinator.go:487-539):
1. `CompileForNode(ctx, task.NodeID)` 编译 —— **基于接管前 DB 状态**
2. `SupersedeInFlight(...)` —— 其中 `restorePendingDelete(old.ID)` 把被接管移除任务的实例恢复为 `enabled=true`
3. `Send` 下发第 1 步编译的规则集

`CompileForNode` 只编译 `enabled=true` 实例(compiler.go:38 `Where("node_id = ? AND enabled = ?", nodeID, true)`)。

### 触发链路(设计主路径,前端明确允许)
1. 节点 N 有移除任务 `t_A` 处于 confirm_wait,实例 X:`enabled=false, pending_delete=true, pending_delete_task_id=t_A`。t_A Apply 时已把 X 规则从节点 -D 删除。
2. 保护期内用户发起新动作(节点级 dispatch / 移除其他实例 / 回滚 / 人工 approve)。
3. `approveAndDispatch(t_B)` 第 1 步编译:**X 是 enabled=false,不编入** t_B 规则集。
4. 第 2 步 `SupersedeInFlight` 作废 t_A + `restorePendingDelete` → **X 变 `enabled=true, applied=true`**。
5. 第 3 步下发 t_B 规则集(**不含 X**)。
6. t_B Apply 成功 → `handleResult`(coordinator.go:604-605)把该节点所有 `enabled=true` 实例 applied 置 true → **X 被固化为"已应用"**。

### 结果
X 在 DB/前端显示"启用、已应用",但节点上 **X 规则不存在**(t_A 已删, t_B 未含)。状态不一致**确定性存在**,直到下次 OnSync 自愈(重新编译含 X 并下发)或用户再次 dispatch 才收敛。窗口期内用户被误导"X 已生效"。

### 同样受影响路径
所有走 `approveAndDispatch` 的接管:节点级 dispatch、SubmitRemoval(新移除)、SubmitRuleSet(回滚,规则集为历史快照更不会含 X)、人工 Approve。

### 修复建议(需确认)
**方案 B(推荐)**:保留"编译失败不动旧任务"(第 1 次编译作可行性验证),SupersedeInFlight 之后若发生接管(返回非空列表)则**重新编译一次**再 Send。
- 改动集中在 `approveAndDispatch`:接管返回非空时,重走编译分支(回滚任务用快照,普通任务重编译)。
- 代价:每次接管多一次 CPU 密集编译,可接受。
- 保持"编译失败不动旧任务"语义不变。

**方案 A**:把 SupersedeInFlight 移到编译之前。缺点:编译失败时旧任务已被接管(丢失保护期),违背方案文档"编译失败不动旧任务"。

**方案 C(最小)**:`restorePendingDelete` 在 Supersede 场景下把实例恢复为 `enabled=true, applied=false`(而非 true)。X 至少不误显示"已应用",但 t_B 仍不含 X,需再 dispatch 一次才恢复,窗口仍在。

### 测试缺口
`TestSupersedeInFlight_ConfirmWaitRemovalRestoresInstance`(coordinator_test.go:262)只断言实例恢复 `enabled=true`,**未断言新任务规则集包含恢复实例**。需补:接管后编译结果必须包含被恢复实例 → 红测试先行。

## P2:autoRollback 与 SupersedeInFlight 并发竞态

`autoRollback`(coordinator.go:688-711)的"读 status → sendRollback → Save rolled_back"与 SupersedeInFlight 的"Save superseded → sendConfirm"非原子。定时器恰好触发(goroutine 已启动)与用户操作并发时:
- DB 最终状态取决于写顺序(rolled_back 或 superseded);
- Agent 可能先收 Rollback(恢复快照)再收 Confirm(释放),或反之;
- 节点被回滚到旧状态,随后 t_B Apply 覆盖。

窗口极窄,最终新任务收敛,自愈兜底。**建议**:SupersedeInFlight 内先 `cancelTimer` 再改状态并持久化(顺序微调),或 autoRollback 用条件更新 `UPDATE ... WHERE status='confirm_wait'`(CAS)。低优先。

## P2:批量 Submit 同节点多任务互斥

Submit(AutoApprove)循环逐个 approveAndDispatch(coordinator.go:202-210):同节点两个 task 时,后者 SupersedeInFlight 会看到前者在 dispatching/applying → 返回 ErrNodeBusy → 后者失败。
- 前端 dispatch 单节点单任务,不触发;
- 策略应用侧若同一节点重复出现在 nodeIDs 才触发。低风险,可加注释说明即可。

## P3:审计细节

1. `task.superseded` result=`pending`(coordinator.go:825):superseded 是终态,用 pending 表达"待新任务确认",可接受。
2. 方案文档设计的"新 task submit detail.superseded=[旧任务列表]"未实现,实际靠旧任务 detail.superseded_by 反查。差异非 bug。

## P3:前端 toggleEnabled 409 后状态残留

PUT(改 DB)成功 → dispatch 409(节点执行中)失败 → enabled 已翻转但未下发,前端刷新显示新状态。409 已明确提示"稍候重试",可接受。nodeBusy 时按钮已禁用,正常不触发。

## 走查确认无问题的点(记录)

- `SupersedeInFlight` 排除 `id != newTaskID` 自身(coordinator.go:798),避免新任务被自己接管。
- `dispatching/applying` 拒绝接管 → ErrNodeBusy → server 409(dispatch + DELETE 两入口均 errors.Is 映射,`template_routes.go:456,589`),不误作废执行中任务。
- 编译失败(第 1 次)markFailed 不动旧任务,旧任务继续保护期,符合设计。
- 旧任务 TaskResult 迟到(status=superseded ≠ applying)→ handleResult 忽略,安全。
- `restorePendingDelete` 按 `pending_delete_task_id` 精确匹配,不会误恢复其他任务关联实例。
- Agent 离线时 sendConfirmToAgent 失败被忽略:旧任务已 superseded 不再回滚,Agent 侧残留快照仅内存泄漏(无害,TaskId 唯一)。
- 前端 `recentSuperseded` 取最新一条(getTasks superseded 按 created_at DESC),banner 指向正确。
- 前端 nodeInGuard 仅算 confirm_wait、nodeBusy 算 dispatching/applying,接管提示与按钮禁用分离正确。
