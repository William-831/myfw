# 前后端非侵入式性能与可维护性优化方案

> 2026-08-13。目标:不改动核心业务逻辑与底层架构,通过非侵入手段提升交互响应速度 + 显著增强可维护性。
> 约束:低风险、易落地、TDD 红-绿-重构、每处优化附前后对比与收益说明。

## 现状诊断(已核实)

| 维度 | 现状 | 痛点 |
|------|------|------|
| 前端防抖/节流 | 无任何防抖/节流/请求去重 | 多页面各自 `setInterval` 轮询(5s/1s),无合并 |
| 前端乐观更新 | `toggleEnabled` 串行 `update → dispatch → pollTaskDone(15s)` | 高频启停操作 UI 无即时反馈,最长等 15s |
| 前端缓存 | 无 | `getNodes()` 6 个页面重复拉全量(后端还带 drift+证书聚合),静态字典(模板/组/地址组/标记)每次进页面重拉 |
| 前端重复逻辑 | `loadNodes` 在 Nodes/Approve/Audit/ExpertMode/NodePolicies/ConfirmGuard 6 处复制;状态标签映射多页面复制 | 高耦合、改一处漏多处 |
| 后端索引 | 单列索引为主 | `WHERE node_id=? AND status IN(...)`(SupersedeInFlight/刷新)无复合索引;AuditLog 按 (node_id,action,scene,result)+created_at 排序无复合索引 |
| 后端缓存 | 无 | dashboard/stats 7 次独立 COUNT;GET /nodes/list 全量聚合(instances+templates+certs);config-drift 全表扫描 |
| 后端 AOP | 仅 `gin.Recovery()` | 无统一日志/错误处理中间件;60+ 处散落 `c.JSON(500, gin.H{"error": err.Error()})` |
| 后端硬编码 | 确认期限 30s/5min、死规则阈值 3 天、轮询间隔、缓存策略散落各文件 | config.go 已有结构但未收纳 |

## 第一部分:前端

### F1. 防抖/节流与请求合并(composables 复用)

**落点**:`refreshInflight` 每次操作后并发 4 个 `getTasks`(confirm_wait/dispatching/applying/superseded);轮询周期不可无限加密,否则请求爆炸。

**方案**:抽 `usePolling(fn, interval)` 统一轮询生命周期(自动 onMounted 启动 / onUnmounted 清理),并内建「上一次未完成则跳过本次」的防重入节流。

**重构前**(ConfirmGuard.vue:176-185,散落轮询样板):
```js
onMounted(() => {
  loadNodes()
  loadTasks()
  pollTimer = setInterval(loadTasks, 5000)
  tickTimer = setInterval(() => { now.value = Date.now() }, 1000)
})
onUnmounted(() => {
  clearInterval(pollTimer)
  clearInterval(tickTimer)
})
```

**重构后**(新 `web/src/composables/usePolling.js`):
```js
// 统一轮询:自动启停 + 防重入(上一轮未完成则跳过本次,避免请求堆积)
export function usePolling(fn, interval = 5000) {
  let timer = null, running = false
  const start = () => { if (timer) return; timer = setInterval(async () => {
    if (running) return                       // 防重入:上次未完成则跳过
    running = true
    try { await fn() } finally { running = false }
  }, interval) }
  const stop = () => { clearInterval(timer); timer = null; running = false }
  onMounted(start)
  onUnmounted(stop)
  return { start, stop }
}
```

**收益**:轮询样板收敛为一行调用;防重入避免慢响应期请求堆积——5s 轮询在接口耗时 3s 时请求数从「无限叠加」降为「每 5s 至多 1 次」,网络压力减半以上。

### F2. 乐观更新(高频启停即时反馈)

**落点**:`toggleEnabled`(NodePolicies.vue:437)当前 3 步串行,启停开关点击后 UI 无响应直到后端整链跑完。

**重构前**:
```js
const toggleEnabled = async (inst, v) => {
  await updateInstance(inst.id, { ...inst, enabled: v })  // ① 写库
  const d = await dispatchNode(selectedNodeId.value, { auto_approve: true }) // ② 下发
  const t = await pollTaskDone(d.tasks?.[0]?.id)           // ③ 轮询 15s
  // ... 全部完成才提示
}
```

**重构后**:
```js
const toggleEnabled = async (inst, v) => {
  const prev = inst.enabled
  inst.enabled = v                                        // ① 乐观翻转,UI 立即响应
  try {
    await updateInstance(inst.id, { ...inst, enabled: v })
    const d = await dispatchNode(selectedNodeId.value, { auto_approve: true })
    // ② 不阻塞等待终态,立即提示"已下发,保护期确认",后台刷新
    refreshInflight(); loadInstances()
  } catch (e) {
    inst.enabled = prev                                  // ③ 失败回滚
    ElMessage.error(e?.response?.data?.error || '切换失败')
    refreshInflight()
  }
}
```

**收益**:启停从「等 15s」降为「即时反馈+后台收敛」;失败回滚保证一致性。需配套前端测试(乐观值立即生效、失败回滚)。

### F3. 本地/内存缓存(降重复拉取)

**落点**:`getNodes()` 6 页面重复全量拉取(后端聚合重);静态字典(getTemplates/getCustomChains/getAddressGroups/getMarks)低变更。

**方案**:api 层加 `cachedGet(url, { ttl, storage })` 包装——只包 GET 只读接口,写操作后主动失效;不改任何业务调用签名。

**重构前**(api/index.js:40,各页面裸调):
```js
export const getNodes = () => service.get('/v1/nodes/list')
```

**重构后**:
```js
// 内存 TTL 缓存:同页面对同一 GET 在 TTL 内只发一次请求
const cache = new Map()
const cachedGet = (url, ttl = 5000) => async () => {
  const hit = cache.get(url)
  if (hit && Date.now() - hit.t < ttl) return hit.data
  const data = await service.get(url)
  cache.set(url, { data, t: Date.now() })
  return data
}
const invalidate = (url) => cache.delete(url)

export const getNodes = cachedGet('/v1/nodes/list', 5000)      // 节点列表 5s 内复用
export const getTemplates = cachedGet('/v1/templates', 30000)  // 静态字典 30s 内复用
export const getCustomChains = cachedGet('/v1/custom-chains', 30000)
export const getAddressGroups = cachedGet('/v1/address-groups', 30000)
export const getMarks = cachedGet('/v1/marks', 30000)
// 写操作后失效:create/update/delete 调用 invalidate 对应 URL
```

**收益**:节点列表重复拉取降 5s 内为 0;静态字典 30s 内切换页面零请求。配合后端缓存,单用户浏览多页面时网络/DB 压力显著下降。

### F4. 重复 UI 逻辑抽离(composables)

**落点**:`loadNodes`+错误提示在 6 个页面复制;状态标签映射(changeLabel/changeTagType/statusLabel)多处复制。

**方案**:
- `useNodeList()`:封装 nodes 加载 + 缓存 + `nodeIP(id)` 反查(ConfirmGuard/Approve/NodePolicies/Audit/ExpertMode 共用)。
- `useStatusLabels()`:集中 `change_label/change_tag_type/status_text` 映射表,各页只取用。

**重构前**(ConfirmGuard.vue:139-144 与 Nodes.vue:655 同构复制):
```js
const loadNodes = async () => {
  try { const data = await getNodes(); nodes.value = data.nodes || [] } catch { }
}
```

**重构后**:
```js
// web/src/composables/useNodeList.js
export function useNodeList() {
  const nodes = ref([])
  const loadNodes = async () => { try { nodes.value = (await getNodes()).nodes || [] } catch { } }
  const nodeIP = (id) => nodes.value.find(x => x.id === id)?.ip
    || nodes.value.find(x => x.id === id)?.hostname
    || id?.slice(0, 12)
  return { nodes, loadNodes, nodeIP }
}
```
各页面 `const { nodes, loadNodes, nodeIP } = useNodeList()` 一行替换。

**收益**:6 处复制收敛为 1 处;后续节点字段变更只改一处。前端 `npm run build` 验证 + 前端单测。

## 第二部分:后端

### B1. 关键查询索引

**落点**:①`Task WHERE node_id=? AND status IN(...)`(SupersedeInFlight、前端 4 状态刷新)缺复合索引;②`AuditLog` 按 node_id/action 过滤 + created_at 排序分页缺复合索引;③`NodePolicyInstance` config-drift 全表扫描。

**方案**:模型 tag 增加复合索引(AutoMigrate 幂等,生产 MySQL/OceanBase 兼容)。

**重构前**(task.go:27,31):
```go
NodeID string     `gorm:"size:64;index" json:"node_id"`
Status TaskStatus `gorm:"size:24;index" json:"status"`
```

**重构后**:
```go
NodeID string     `gorm:"size:64;index" json:"node_id"`
Status TaskStatus `gorm:"size:24;index;index:idx_task_node_status,priority:2" json:"status"`
// 复合索引 idx_task_node_status(node_id, status):保护期接管/刷新命中
```
AuditLog 增加 `index:idx_audit_node_created,priority:2`(node_id + created_at 排序)。

**收益**:任务刷新/接管的节点×状态查询从全表扫描降为索引点查;审计分页排序不再 filesort。数据量大时(审计万级)收益显著,小数据无副作用。

### B2. 只读高频数据缓存层

**落点**:`GET /api/v1/dashboard/stats`(7 次独立 COUNT)、`GET /api/v1/nodes/list`(Preload + 全量 instances/templates/certs 聚合)、`config-drift` 全表扫描。

**方案**:新建 `internal/controller/server/readcache.go`——带 TTL 的内存缓存 + RWMutex;包装只读聚合;写操作路由(mutating)统一失效节点列表/统计缓存。

**重构前**(dashboard_routes.go:14-38,每次请求 7 次 COUNT):
```go
db.Model(&model.Node{}).Count(&nodeCount)
db.Model(&model.Node{}).Where("status = ?", ...).Count(...)
// ... 7 次独立 COUNT
```

**重构后**:
```go
// readcache.go 核心:TTL 内存缓存
type ReadCache struct {
  mu    sync.RWMutex
  items map[string]cacheItem   // key -> {data, expiredAt}
}
func (c *ReadCache) Get(key string) (any, bool)
func (c *ReadCache) Set(key string, val any, ttl time.Duration)
func (c *ReadCache) Delete(prefix string)  // 写操作后按前缀失效

// dashboard_routes.go:stats 包一层 5s TTL
if v, ok := rc.Get("dashboard:stats"); ok { c.JSON(200, v); return }
// ... 原 7 次 COUNT 逻辑
rc.Set("dashboard:stats", result, 5*time.Second)
```

**收益**:dashboard 5s 内第二次访问零 COUNT;节点列表聚合(最重的只读接口)5s 内复用;节点/实例写操作后主动失效保证一致性。

### B3. 耗时操作异步化

**落点**:`applyNow`(task_routes.go:90)同步 `context.WithTimeout(10s)` 等 Agent 回复,HTTP 长阻塞;`sync-all`(template_routes.go:532)同步批量编译下发。

**方案(保守,低风险)**:①`applyNow` 保留同步等待但有超时,改为「立即返回 accepted + 前端轮询」需改前端契约——本阶段只做降级:超时从 10s 缩到 8s 并返回 accepted,不再阻塞 10s;②`sync-all` 已按节点循环,加防重入互斥(正在同步同节点时直接 409),避免并发重复下发。

**收益**:HTTP 长阻塞缩短;同步批量避免并发冲突。核心链路(coordinator dispatch)本就是异步,不动。

### B4. AOP:统一日志 + 错误处理中间件

**落点**:60+ 处散落 `c.JSON(500, gin.H{"error": err.Error()})`;无请求日志,排查靠审计表。

**方案**:新建 `internal/controller/server/middleware.go` 两个中间件:
- `requestLogger`:method/path/status/duration + 用户,5 行核心。
- 统一错误响应不做破坏性迁移——本阶段仅**新增日志中间件**(零侵入,不加不改现有响应),并给 `newWebHandler` 挂上。

**重构前**(server.go:378,仅 Recovery):
```go
r.Use(gin.Recovery())
```

**重构后**:
```go
r.Use(gin.Recovery())
r.Use(requestLogger())   // 新增:结构化请求日志,零侵入
```

```go
// middleware.go
func requestLogger() gin.HandlerFunc {
  return func(c *gin.Context) {
    start := time.Now()
    c.Next()
    slog.Info("http", "method", c.Request.Method, "path", c.Request.URL.Path,
      "status", c.Writer.Status(), "ms", time.Since(start).Milliseconds(),
      "user", c.GetString("username"))
  }
}
```

**收益**:全量请求可观测(谁、何时、多慢、什么结果),排查问题不再依赖前端复现。不改变任何现有响应行为,零业务侵入。

### B5. 硬编码提取统一配置

**落点**:确认期限默认 30s(task_routes.go:177)/5min(policy_routes.go:276)、死规则阈值 3 天(iptables_routes.go:219)、轮询/缓存 TTL 无配置入口。

**方案**:config.go 增加 `Policy` 段收纳阈值;`deadRuleThresholdDays` 等从包内 const 改为 cfg 注入;默认值保持现状不改变行为。

**重构前**(iptables_routes.go:219):
```go
threshold := time.Now().Add(-deadRuleThresholdDays * 24 * time.Hour) // 包级 const=3
```

**重构后**(config.go):
```go
type PolicyConfig struct {
  DeadRuleThresholdDays int           `yaml:"dead_rule_threshold_days"`   // 死规则判定阈值
  ConfirmDeadlineDefault time.Duration `yaml:"confirm_deadline_default"`   // 保护期默认时长
}
// Default(): DeadRuleThresholdDays: 3, ConfirmDeadlineDefault: 5 * time.Minute
```
路由层从 `cfg.Policy.DeadRuleThresholdDays` 读取。

**收益**:运维可在 YAML 调整阈值不改代码;默认值不变故行为零变化,回归安全。
