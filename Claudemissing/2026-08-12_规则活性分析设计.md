# 规则活性分析设计(命中率采集 + 死规则识别)

> 2026-08-12 创建。三大痛点方案计划一,最后一个落地。本设计基于代码核查修正了
> `2026-08-11_平台治理三大痛点方案.md` 中过时的行号与假设(见"现状核查")。

## 摘要

给每条 MYFW 规则追加 `comment` 标识(编码实例 ID),Agent 周期采集 `iptables -L -v -n -x`
解析 pkts/bytes + comment,Controller 按 (node, instance_id) upsert 命中统计,
启用超阈值且 packets=0 的规则标记为死规则,前端展示命中率 + 死规则徽标。

## 方案

### 传输通道:复用 HTTP(不动 proto/gRPC)

原方案设想的 gRPC `StateReport.rule_hits` 通道未启用,启用需动 proto + agent conn + stream,
改动面大。改为**复用既有 HTTP 上报通道**:

- 现状:`reportIptablesRules`(agent main.go:275)启动后 sleep 2s 采集一次 `iptables -S`,
  POST 到 `/api/v1/iptables/report/:node_id`。
- 改造:新增 `reportRuleHits` 周期循环(60s),采集 `iptables -L -v -n -x --line-numbers`,
  解析 pkts/bytes + comment,POST 到 `/api/v1/iptables/hits/:node_id`。
- proto 不动(`RuleHit` 预留暂不启用,未来 gRPC 化再启用,避免过度设计)。

### 1. driver:规则追加 comment

`compileRule`(iptables.go:628)在返回 args 前追加:
```go
args = append(args, "-m", "comment", "--comment", "myfw:"+r.Id)
```
- `r.Id` 形如 `i42`/`i42-acl`/`i42-drop`,comment = `myfw:i42`/`myfw:i42-acl`。
- 位置:统一加在 target(`-j ...`)之后,确保 `iptables -S` 输出位置稳定(hash 稳定)。
- nftables driver 等价:nft 原生支持 `comment "myfw:i42"` 关键字,加在规则末尾。

### 2. collector:计数器采集 + comment 解析

collector 新增 `CollectRuleHits() ([]RuleHitStat, error)`:
- 执行 `iptables -t filter -L -v -n -x --line-numbers`(filter 表首版,nat/mangle 后续)。
- 解析每行:`pkts bytes target prot opt in out source destination` + 末尾 `/* myfw:i42 */`。
- 仅保留 comment 以 `myfw:` 开头的行,提取实例 ID(`i42-acl` -> `42`)。
- 返回 `[]RuleHitStat{InstanceID, Packets, Bytes}`。

新增 `RuleHitStat` 内部结构(collector 包,非 model):
```go
type RuleHitEntry struct {
    InstanceID uint
    Packets    int64
    Bytes      int64
}
```

### 3. agent main:周期上报

新增 `reportRuleHits(ctx, cfg, nodeID, log)`:
- 60s ticker 循环,调 `collector.CollectRuleHits()`,POST JSON 到 `/api/v1/iptables/hits/:node_id`。
- 启动时 `go reportRuleHits(...)` 与 `reportIptablesRules` 并行。

### 4. Controller:model + API

**新增 model** `internal/model/rule_hit.go`:
```go
type RuleHitStat struct {
    ID         uint      `gorm:"primaryKey"`
    NodeID     string    `gorm:"index:idx_node_inst,unique;size:64"`
    InstanceID uint      `gorm:"index:idx_node_inst,unique"`
    Packets    int64
    Bytes      int64
    LastSeen   time.Time `gorm:"index"`
    CreatedAt  time.Time
    UpdatedAt  time.Time
}
```
- 按 (node_id, instance_id) 唯一索引 upsert。

**API** `internal/controller/server/iptables_routes.go` 新增:
- `POST /api/v1/iptables/hits/:node_id`:接收 Agent 上报,upsert RuleHitStat。
- `GET /api/v1/nodes/:id/rule-hits`:返回节点所有实例命中率(关联 NodePolicyInstance)。

**死规则判定**(查询时计算,不落库):
- 实例 `enabled=true` + `RuleHitStat.packets=0` + 实例 `created_at` 距今 > 7 天(可配) -> `dead=true`。
- 阈值放 `SystemSetting` key=`rule_hit.dead_threshold_days`,默认 7。

### 5. 前端

`web/src/views/NodePolicies.vue` 实例列表:
- 加"命中率"列(packets + bytes)+ 死规则徽标(灰色"死规则"标签)。
- 加"仅看死规则"过滤开关。
- `web/src/api/index.js` 加 `getNodeRuleHits(nodeId)`。

## hash 兼容(关键风险,已论证无需特殊处理)

`Driver.Snapshot` 基于规则文本 hash,加 comment 后文本变化,hash 变。但:

- **存量节点**:旧规则无 comment + 旧 expected_hash 无 comment = 一致,不误报 drift。
- **新 Apply 后**:新规则含 comment + 新 expected_hash 含 comment = 一致。
- **跨版本瞬间**(driver 升级但未重新 Apply):规则仍是旧的(无 comment),expected_hash 也是旧的,一致。

结论:Apply 自然收敛,无需 strip comment。保留备选:若未来要求 comment 不影响 hash 语义,
在 `Snapshot` 生成 payload 时 strip `-m comment --comment "myfw:..."` 段(选项 A)。

## TDD 用例规划

### collector_test.go(解析纯函数,表驱动)
1. 标准 `-L -v -n -x` 行 + `/* myfw:i42 */` -> InstanceID=42, pkts, bytes 正确。
2. 无 comment 的行(系统规则)-> 跳过。
3. 非 `myfw:` 前缀 comment -> 跳过。
4. `i42-acl` -> InstanceID=42(取 `-` 前数字)。
5. 空输出 -> 空切片无错。
6. filter 表多链混合 -> 全部解析。

### iptables_routes_test.go
1. POST hits 上报 -> upsert RuleHitStat(同 node+instance 二次上报更新 packets)。
2. GET rule-hits -> 返回实例命中率 + dead 标记(packets=0 且超阈值)。
3. GET rule-hits -> enabled=false 实例不标 dead。
4. GET rule-hits -> packets>0 不标 dead。

### driver compileRule 测试(回归)
1. compileRule 输出含 `-m comment --comment "myfw:i42"`。
2. comment 位置在 target 之后(hash 稳定)。

## 风险与对策

| 风险 | 对策 |
|------|------|
| comment 改变规则 hash | 已论证自然收敛,无需特殊处理(见上) |
| nftables comment 落盘/回读 | 需验证 nft 驱动;首版若 nft 节点少可仅 iptables,标注 nft 为 P2 |
| `-L -v -n -x` 解析格式差异(不同 iptables 版本) | 解析容错:按字段数 + 末尾 comment 正则;加样例测试覆盖 |
| 采集频率 60s 对节点负载 | iptables -L 轻量,60s 可接受;可配 |
| 存量规则无 comment,首次采集拿不到实例 ID | 重新 Apply 后才有 comment;存量节点命中率从下次 Apply 起开始统计,可接受 |
| 死规则阈值 7 天对新建实例误判 | 用 created_at 判存活,新建实例不标 dead |
