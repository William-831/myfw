# 2026-08-14 MARK 白名单同端口多实例覆盖冲突修复

## 摘要

修复 MARK 白名单拦截在**同一节点、同一端口配置多条实例(不同 mark、不同源组)**时,打标规则互相覆盖导致先配置的白名单失效的 bug。同时排查确认用户此前反馈的"组外 IP 能访问"现象为节点绑定错位(配置问题),非规则逻辑 bug。

## 背景与根因

### 用户现象(已排查,非代码 bug)
用户反馈"MARK 白名单引用地址组后,组外 IP 反而能访问 22"。249 实测 + 审计日志确认:
- 实例「允许ssh」(MARK, INPUT, 端口 22, 源组 192.168.80.248)绑定并下发到节点 248「测试服务器2」(审计 `06:13 dispatch -> n_928ff=192.168.80.248`)
- 用户在 249 验证:249 上无该实例规则(无 MARKACL-IN 链),22 端口对所有 IP 默认放行
- **根因 = 节点绑定错位**(前端以节点为中心,创建实例时误选 248),规则逻辑经 `TestCompileMarkWhitelistWithAddressGroup` 验证正确(组内 ACCEPT / 组外 DROP)

### 本次修复的 bug(真实代码 bug)
`compiler.go` compileInstance 白名单分支原设计:
- 打标规则:清空 source/source_group,**无条件按端口打标**("端口标识")
- 兜底 DROP:带 `match_mark=inst.Mark` 拦截

同端口两条实例(如 mark 15 源组A、mark 255 源组B)时,打标规则按 priority 先后执行,第二条无条件覆盖第一条 mark → 先配置实例的 ACCEPT(mark 不匹配)/DROP 全部失效,其组内成员被后实例的兜底 DROP 误杀。

## 修复方案(不碰 proto/driver,只改 compiler + 测试)

反转设计,打标从"端口标识所有源"改为"按端口+源组只给白名单源打标":
1. **打标规则保留 source/source_group**:只给本实例白名单源打标,不同实例(不同源组)打不同 mark 互不覆盖
2. **兜底 DROP 改带 PortRange、不带 mark**:priority 远偏移 `markAclDropOffset = 1<<20`,确保在所有白名单 ACCEPT 之后,拦截"访问该端口但未命中任何白名单"的流量

单实例行为不变(源在组内放行、组外拦截),多实例各自独立生效。

## 产出

- `internal/controller/compiler/compiler.go`:新增 `markAclDropOffset` 常量;compileInstance 白名单分支打标保留源、DROP 改带端口+offset
- `internal/controller/compiler/mark_whitelist_test.go`:
  - `TestCompileMarkWhitelistWithAddressGroup`(新增):复现用户地址组场景,验证规则逻辑正确
  - `TestCompileMarkWhitelist_MultiSamePortConflict`(新增,先红后绿):复现覆盖 bug,修复后三态验证(源A放行/源B放行/其他拦截)
  - `TestCompileMarkWhitelist` 断言更新(打标带源组、DROP 带端口)

## 验证

- 全部测试通过:`go test ./internal/controller/... ./internal/agent/driver/...`
- `go build ./...` 通过

## 决策记录

- 不新增 proto 字段(proto 工具链 protoc/protoc-gen-go 缺失且安装失败),用"打标带源组 + DROP 带端口 priority 偏移"实现,避免手动改 pb.go 的风险
- 偏移量 1<<20 足够覆盖单节点合理实例规模,注释说明设计意图
